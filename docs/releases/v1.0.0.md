# Notas da release v1.0.0 — rascunho

`v1.0.0` é o primeiro baseline estável do Terraform GCP .NET Blueprint. Ele consolida o repositório como arquitetura de referência coerente, e não como coleção de módulos isolados.

> Este documento está preparado para revisão. Ele não publica tag nem GitHub Release.

## Destaques

### Composição completa dos ambientes

O repositório inclui roots completos `dev` e `prod` que compõem Cloud Run services/jobs, Pub/Sub, Secret Manager, IAM, rede privada, Memorystore for Redis e políticas de alerta do Cloud Monitoring.

As diferenças entre ambientes são explícitas em vez de escondidas nos módulos: desenvolvimento favorece sizing orientado a custo, enquanto produção demonstra padrões orientados a HA/capacidade.

### Entrega GitHub-to-GCP sem chaves

GitHub Actions autentica com OIDC e Workload Identity Federation. Nenhuma chave JSON de service account é necessária.

Pull requests permanecem sem credenciais. Workflows manuais de plan/apply executam a partir da `main`, inicializam o backend GCS real e usam identidade dedicada de deployment. Apply adiciona confirmação, controles de mudanças destrutivas, gate de GitHub Environment e verificação de fingerprint após re-plan.

### Rede privada e cache

Cloud Run services/jobs usam Direct VPC egress. Memorystore for Redis é conectado via Private Service Access, com AUTH/TLS habilitados e proteção contra exclusão no provider. Produção compõe `STANDARD_HA` por padrão.

### Limites explícitos de identidade e segredos

Workloads API, worker e batch usam identidades de runtime separadas. Pub/Sub push e Scheduler usam identidades de transporte distintas. Acesso ao Secret Manager é restrito por segredo.

Terraform gerencia containers/relações de acesso dos segredos, mas deliberadamente não cria versões de payloads dos segredos da aplicação. Payloads de Redis AUTH e CA também ficam fora dos outputs Terraform.

### Observabilidade operacional

O conjunto baseline de alertas cobre:

- taxa HTTP 5xx do Cloud Run;
- idade da mensagem Pub/Sub não confirmada mais antiga;
- encaminhamento dead-letter;
- execuções com falha de Cloud Run Jobs;
- pressão de memória Redis;
- conexões Redis rejeitadas.

Logging estruturado, semântica de tracing e SLOs reais do produto permanecem responsabilidades da aplicação/time.

### Governança do repositório

O baseline inclui:

- formatação/validação/testes nativos Terraform;
- TFLint;
- scan IaC Trivy HIGH/CRITICAL;
- pins imutáveis de GitHub Actions;
- Dependabot para Actions e dependências Terraform;
- procedimentos documentados de deployment/recovery/troubleshooting.

## Comportamento importante de ciclo de vida

A criação de ambiente usa duas fases:

1. fundação com `enable_workloads=false`;
2. bootstrap externo das versões dos segredos seguido de ativação unidirecional dos workloads.

Depois que a ativação é aplicada como `true`, a flag não pode ser usada para desativar o ambiente. Isso impede teardown parcial de workloads protegidos e recursos dependentes de mensageria/trigger.

## O que a v1.0.0 não afirma

A release não afirma que o sizing padrão de produção seja adequado para todo sistema. Também não fornece infraestrutura de edge público, builds dos containers da aplicação, arquitetura de banco, política organizacional, rotação de segredos, SLOs universais, testes de carga/chaos ou workflows automáticos de manipulação/destroy de state.

Um CI offline bem-sucedido comprova contratos do repositório, não execução real na cloud. A issue #29 acompanha separadamente a evidência necessária para afirmar plan de backend/provider autenticado via WIF contra projeto real de desenvolvimento.

## Notas de upgrade/adoção

Este é o primeiro baseline estável, portanto não existe caminho de migração a partir de versão estável anterior. Novos usuários devem seguir `docs/production-readiness.md` do bootstrap de state/WIF até ativação do ambiente.

Usuários experimentais existentes devem comparar:

- prefixos de backend e ownership de state;
- identificadores/restrições de ref da confiança WIF;
- estado de ativação unidirecional dos workloads;
- tier/proteção contra exclusão do Redis;
- relações explícitas de identidade de runtime/transporte;
- repository variables consumidas pelos workflows de deployment;
- ownership de canais de notificação fora do state Terraform do ambiente.

## Antes de publicar

Revise o checklist de prontidão da release em `docs/production-readiness.md`, o CI atual da `main`, threads de review não resolvidas e as evidências da issue #29. Crie a tag/release somente como ação humana explícita.
