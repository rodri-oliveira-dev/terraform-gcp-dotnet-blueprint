# v1.0.0 release notes — draft

`v1.0.0` is the first stable baseline of the Terraform GCP .NET Blueprint. It packages the repository as a coherent reference architecture rather than a collection of isolated modules.

> This document is prepared for review. It does not publish a tag or GitHub Release.

## Highlights

### Complete environment composition

The repository now includes complete `dev` and `prod` roots that compose Cloud Run services/jobs, Pub/Sub, Secret Manager, IAM, private networking, Memorystore for Redis and Cloud Monitoring alert policies.

Environment differences are explicit rather than hidden in modules: development favors cost-conscious sizing while production demonstrates HA/capacity-oriented defaults.

### Keyless GitHub-to-GCP delivery

GitHub Actions authenticates with OIDC and Workload Identity Federation. No service-account JSON key is required.

Pull requests remain credential-free. Manual plan/apply workflows run from `main`, initialize the real GCS backend and use a dedicated deployment identity. Apply adds confirmation, destructive-change controls, GitHub Environment gating and a re-plan fingerprint check.

### Private networking and cache

Cloud Run services/jobs use Direct VPC egress. Memorystore for Redis is attached through Private Service Access, with AUTH/TLS enabled and provider-level deletion protection. Production composes `STANDARD_HA` by default.

### Explicit identity and secret boundaries

API, worker and batch workloads use separate runtime identities. Pub/Sub push and Scheduler use separate transport identities. Secret Manager access is scoped per secret.

Terraform manages secret containers/access relationships but deliberately does not create application secret payload versions. Redis AUTH and CA payloads are also kept outside Terraform outputs.

### Operational observability

The baseline alert set covers:

- Cloud Run HTTP 5xx ratio;
- Pub/Sub oldest-unacked age;
- dead-letter forwarding;
- failed Cloud Run Job executions;
- Redis memory pressure;
- rejected Redis connections.

Structured logging, tracing semantics and actual product SLOs remain application/team responsibilities.

### Repository governance

The baseline includes:

- Terraform formatting/validation/native tests;
- TFLint;
- Trivy HIGH/CRITICAL IaC scanning;
- immutable GitHub Actions pins;
- Dependabot for Actions and Terraform dependencies;
- documented deployment/recovery/troubleshooting procedures.

## Important lifecycle behavior

Environment creation uses two phases:

1. foundation with `enable_workloads=false`;
2. external secret-version bootstrap followed by one-way workload activation.

After activation has been applied as `true`, the flag cannot be used to deactivate the environment. This prevents partial teardown behavior around protected workloads and dependent messaging/trigger resources.

## What v1.0.0 does not claim

The release is not a claim that the default production sizing is appropriate for every system. It also does not provide public-edge infrastructure, application container builds, database architecture, organization policy, secret rotation, universal SLOs, load/chaos testing or automated state surgery/destroy workflows.

A successful offline CI run proves repository contracts, not real cloud execution. Issue #29 separately tracks the evidence required to claim successful WIF-authenticated backend/provider planning against a real development project.

## Upgrade/adoption notes

This is the first stable baseline, so there is no prior stable-version migration path. New adopters should follow `docs/production-readiness.md` from state/WIF bootstrap through environment activation.

Existing experimental adopters should compare:

- backend prefixes and state ownership;
- WIF trust identifiers/ref restrictions;
- one-way workload activation state;
- Redis deletion protection/tier;
- explicit runtime/transport identity relationships;
- repository variables consumed by deployment workflows;
- notification channel ownership outside environment Terraform state.

## Before publishing

Review the release-readiness checklist in `docs/production-readiness.md`, current CI on `main`, unresolved review threads and issue #29 evidence. Then create the tag/release only as an explicit human action.
